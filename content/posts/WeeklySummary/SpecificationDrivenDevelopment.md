在上一篇文章[《在这个直奔 AGI 的时代，学点编程吧》](/posts/weeklysummary/studysoftwareinagiera/)中，我们聊到了当下 AI 辅助编码的一个核心痛点：

> **“一个工程能力差的人，搭配上 AI 后，产出屎山的效率可以达到先前的数倍。”**

当大语言模型的编码速度越来越快、代码生成变得廉价到唾手可得时，软件开发的核心矛盾已经悄然发生了转移：**瓶颈不再是“代码写得有多慢”，而是“如何确保 AI 写出的代码符合系统的真实预期，且不会在三轮迭代后坍塌成不可维护的屎山”。**

为了解决这一问题，业界正在发生一场被称为 **“权力倒置（The Power Inversion）”** 的开发范式变革——**规范驱动开发（Specification-Driven Development，简称 SDD）**。

本文将用通俗精炼的语言，系统性地梳理从 TDD、BDD 到 SDD 的演化脉络、SDD 的核心宗旨与实操方法、如何避坑，以及 AI 时代前沿社区沉淀出的最新实践。

---

## 驱动范式的演进：从 TDD、BDD 到 SDD

要理解 SDD，我们先来看看软件工程史上三次关于“用什么驱动开发”的重要思考跃迁：

![从 TDD、BDD 到 SDD 的演变](/images/zhiyuan_2/tdd_bdd_sdd_evolution.png)

### 1. TDD（Test-Driven Development，测试驱动开发）
* **核心口号**：“红 → 绿 → 重构”。
* **核心命题**：在写业务代码前，先写单测（红），再写极简代码让测试通过（绿），最后优化设计（重构）。它验证的是**代码实现是否符合程序员的技术预期**。
* **局限性**：TDD 过于偏向微观的函数和模块细节。测试全绿的系统，依然可能完全偏离业务的真实需要；另外在实际工程中，手写维护大量的 Mock 和单测极其耗费精力，很多人往往中途放弃。

### 2. BDD（Behavior-Driven Development，行为驱动开发）
* **核心口号**：“Given - When - Then”。
* **核心命题**：使用业务人员也能看懂的通用语言（如 Cucumber/Gherkin），描述系统的外在行为，验证**软件行为是否符合业务方的预期**。
* **局限性**：虽然对齐了业务与开发，但自然语言场景与底层测试胶水代码（Glue Code）之间的维护断层依然巨大。写一套完整的 BDD 流程常常比写业务代码本身还要繁琐。

### 3. SDD（Specification-Driven Development，规范驱动开发）
* **核心变革**：**权力倒置（Power Inversion）**。
* 在传统模式中，“代码是资产，文档是附庸”——我们写的 PRD、技术方案、架构图，往往在代码写完后就停止维护，代码变成了唯一的真理。
* 而在 SDD 看来：**规约（Specification）才是核心资产，代码只是规约在特定语言框架下的编译产物！**

> **一句话区分三者**：
> - **TDD** 问的是：“我写的这段函数对不对？”（偏技术单元）
> - **BDD** 问的是：“这个功能在业务场景下表现是否符合预期？”（偏用户行为）
> - **SDD** 问的是：“整个系统的目标、契约与状态转移是否严谨完备？如果是，那就以此规约为源头，驱动/合成出整套系统与验证网。”（偏全局架构与严谨契约）

## 为什么一定要做 SDD？

在没有 AI 的年代，虽然也有人提倡规范与形式化，但难以落地，因为**人工维护高精度规范并手动翻译成代码的成本过于高昂**。

但当大语言模型（如 Claude 3.7 / GPT-4o / DeepSeek 等）具备了强大的语义理解和代码生成能力后，整个等式发生了质的逆转：

![传统手工开发 vs 规范驱动开发 (SDD)](/images/zhiyuan_2/sdd_vs_traditional_dev.png)

1. **消除无边界幻觉与屎山膨胀**  
   直接用口头 Prompt 让 AI 编程，AI 往往倾向于打补丁（写一层层嵌套的 `if-else`），最后陷入“改好 A 坏了 B”的无限修 Bug 循环。SDD 通过**前置契约约束**，给 AI 戴上了紧箍咒。
2. **人类升维：从码农变为系统总规约师**  
   把打键盘、写样板代码、补齐常规测试这些边际成本极低的事情交给 AI；人类工程师专注于思考**系统的架构边界、数据契约、安全约束与状态转移**。
3. **支持低成本推倒重来（Start-over）与假设实验**  
   有了清晰精准的 Spec，如果明天想把 Python 架构换成 Go，或者把 REST API 升级为 gRPC，核心 Spec 依然有效，只需生成新的计划并重新合成代码即可。

## 怎样落地 SDD？标准工作流与案例

SDD 的核心铁律是：**Define what and why before deciding how to build it（在思考怎么做之前，先严谨定义做什么和为什么做）。**

一个标准的 SDD 闭环包含五个渐进推演阶段：

![规范驱动开发 (SDD) 渐进推演流程图](/images/zhiyuan_2/sdd_pipeline_process.png)

### 完整阶段推演

```text
Specify (What & Why) ──► Plan (How) ──► Tasks (Breakdown) ──► Implement (Execution) ──► Converge (Verify)
```

1. **Specify（定义规约）**：描述业务目标、用户场景以及不可打破的契约（Requirements & Scenarios）。
2. **Plan（架构设计）**：选定技术栈、组件边界、数据模型与接口协议（Design）。
3. **Tasks（任务原子化）**：将方案拆解为机器可连续执行的小任务（每个任务建议 2-5 分钟可交付）。
4. **Implement（依约执行）**：AI Agent 逐个勾选任务并提交实现与测试。
5. **Converge（验收收敛）**：运行完整的验证体系，确认代码与 Spec 100% 契约吻合，并归档进入基线。

### 实操案例：设计一个「优惠券核销服务」

我们通过一个简化的工程实例，看看 SDD 是如何运作的。

#### 第一步：编写规约（`spec.md`）

在这个阶段，**绝对不写一行业务代码，甚至不提用什么数据库**，只定义契约与边界：

```markdown
# 优惠券核销服务规范 (Coupon Redemption Spec)

## 1. 核心需求
系统必须允许合法用户在订单结算时安全核销优惠券，杜绝超额扣减与并发重复核销。

## 2. 核心场景与行为契约 (Given-When-Then)

### 场景一：正常足额核销
- **Given**：用户持有状态为 UNUSED 的满减券（满 100 减 20），订单实付金额为 150 元；
- **When**：用户提交核销请求；
- **Then**：
  - 订单应扣减 20 元，实付变为 130 元；
  - 该优惠券状态原子变更为 USED，记录核销时间与对应订单号；
  - 响应 HTTP 200 及核销凭证。

### 场景二：并发重复核销（防重防刷）
- **Given**：同一个用户在同一毫秒内，针对同一张优惠券发送 2 个并发请求；
- **When**：两个请求同时到达核销网关；
- **Then**：
  - 必须严格保证**有且仅有 1 个请求成功**，另一个请求必须失败；
  - 失败请求返回 HTTP 409（Conflict），提示“优惠券已被使用或状态冲突”；
  - 优惠券账户流水不得出现多扣或负数。
```

#### 第二步：拟定技术方案（`design.md`）

基于上述 Spec，让 AI 与你共同评估架构选型与并发控制方案：

```markdown
# 技术设计：优惠券核销方案

## 技术选型
- **语言框架**：Go + Gin / C++
- **持久化与并发防重**：PostgreSQL 行级锁 (`SELECT ... FOR UPDATE`) 或 Redis 分布式租约锁 + 数据库乐观锁版本号 (`version`)
- **幂等性保障**：以 `biz_id = user_id + coupon_id + order_id` 构建唯一性索引约束。
```

#### 第三步：拆解任务列表（`tasks.md`）

将大目标切碎为确定性的原子任务：

```markdown
- [ ] 1. 编写领域模型与数据库迁移脚本（包含唯一索引与状态机枚举）
- [ ] 2. 依据 Spec 场景编写并发冒烟测试（编写测试框架先行，验证并发抢券下的 409 拦截）
- [ ] 3. 实现带有悲观锁/乐观锁保障的核销 Service 逻辑
- [ ] 4. 运行契约与并发压力测试，验证是否收敛
```

#### 第四步与第五步：执行与收敛（`Implement & Converge`）

交给 Coding Agent（如 Claude Code、Cursor、OpenCode 等）按照任务逐一执行。AI 每写完一段，立刻运行单元测试与静态分析。只有当所有测试绿灯、且并发场景完全符合 Spec 预期时，才算真正**“收敛（Converged）”**。

## 怎样避免 SDD 走偏？（反模式与避坑指南）

很多团队在尝试 SDD 时容易走向极端，需要警惕以下几个陷阱：

### 1. 规约变成“大包大揽的瀑布大文档”（Analysis Paralysis）
- **误区**：以为规范驱动就是要花一个月写一份 200 页的完美 PRD。
- **正道**：**增量式 Delta Spec（差异规约）**。现代 SDD 强调 `Delta` 概念（如 OpenSpec 的思路），每次只针对一个具体的变更（Change）编写新增、修改或废除的条目，小步快跑，持续合并。

### 2. 跨阶段“裸奔”（Skipping Gates）
- **误区**：在 Spec 还没搞清用户边界时，就让 AI “先随便出个版本看看”。
- **正道**：**先对齐意图，再敲定架构，最后才动代码**。在没有得到人类对 Spec/Design 的确认前，坚决禁止生成业务代码。

### 3. 文档与代码脱节（Spec Drifting）
- **误区**：线上发现 Bug，直接去改代码，改完提测上线，Spec 却丢在一旁落灰。
- **正道**：**修改从 Spec 发起**。当业务逻辑变化或遇到未考虑的边缘情况时，首先更新 Spec 中的场景断言，然后重跑计划与任务。代码是 Spec 的下游投影。

### 4. 忽略负面与异常边界（Happy Path Only）
- **误区**：Spec 中只写“点击按钮就成功”，对网络超时、幂等冲突、空指针、限流降级只字不提。
- **正道**：在制定 Spec 时，重点让 AI 审视：“这里的不可行状态有哪些？并发会有什么竞争条件？外部依赖超时如何兜底？”。

### 5. 陷入“过度工程”陷阱（Over-Engineering & YAGNI 沦陷）
- **误区**："虽然规范驱动开发可以节省大量时间和减少技术债务，但也要记住，过度设计也可能导致花费过多时间。如果你花了三周时间讨论一个 JSON 键的名称或某个功能的特定 API 端点，而该功能可能在一个月内就会被删除，这就违背了规范驱动开发的目的。"
- **正道**：不要过分专注于为每种可能的未来建模。青睐轻量级的、不断发展的规范，而不是详尽无遗的“最终”规范。编写行动所需的内容，在代码中快速验证，并随着现实的变化进行迭代。一般原则是，完善规范的成本应始终低于实施中纠正误解的成本。

## 总结：AI 时代的现代工作流与业界最新前沿

在引入大模型与自主编码智能体（Autonomous Coding Agents）之后，SDD 已经不再仅仅是一套纸面方法论，而是演变成为许多顶尖开源工具的核心架构。

业界在这个方向上最具代表性的探索包括：

### 1. GitHub 官方出品：**Spec Kit**
* **项目地址**：[github/spec-kit](https://github.com/github/spec-kit)
* **核心亮点**：GitHub 探索 AI Agentic Coding 的标杆项目。提出了 **“Power Inversion（权力倒置）”** 的旗帜理念：
  * 提供了一套成体系的 Agent Slash Commands：`/speckit-constitution`（设定项目工程公理）、`/speckit-specify`（自然语言提炼严密需求）、`/speckit-plan`（架构决策与技术选型）、`/speckit-tasks`（拆解实施任务）、`/speckit-implement`（代码生成）以及 `/speckit-converge`（收敛验证）。
  * 强调规范不仅用于新功能开发，还通过独立扩展包支持 **Bug 诊断修复（assess → fix → test）** 与 **产品想法论证（idea assessment）**。

### 2. 敏捷型 Spec 框架：**OpenSpec**
* **项目地址**：[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
* **核心亮点**：主打 **“轻量协议层（Lightweight Agreement Layer）”** 与 **“增量规约（Delta Specs）”**：
  * 反对瀑布式的僵硬规约，强调 **“Enablers, not gates（规约是赋能器，而非阻碍流转的死门）”**。
  * 核心心智模型由双目录驱动：`openspec/specs/` 代表当下系统的唯一真理（Source of Truth），而 `openspec/changes/` 则代表每次变更的提案（Proposal、Design、Tasks、Delta Specs）。一旦功能落地通过验证，通过 `/opsx:archive` 自动把差异 Spec 归档合并进主干真理中。
  * 支持跨仓库规划（Stores），适应已有项目（Brownfield Codebase）的渐进式演进。

### 3. 上下文工程系统：**Get Shit Done (GSD)**
* **项目地址**：[gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done)
* **核心亮点**：深度结合 Meta-Prompting 与上下文工程（Context Engineering）。
  * 针对大模型长上下文窗口易发生“认知漂移（Attention Drift）”的问题，通过严格的阶段隔离与 Spec 任务切分，使 Claude Code 等终端 Coding 工具能够始终聚焦在当前极小的子目标上，避免了长对话带来的代码劣化。

## 结语

在蒸汽机时代，人类发明了流水线与机床规约，才使得工业化大规模复制成为可能；在电气时代，标准电路图与接口规范让极其复杂的电子设备得以协同组装。

今天，大模型就是软件工程的“超导发电机”。如果继续用原始松散的口头对话来指挥这台发电机，得到的注定是不可控的电弧与火灾。**只有用严谨的契约、清晰的领域边界和规范驱动（SDD）的闭环机制，才能真正驯服 AI 的算力洪流，在瞬息万变的智能时代中，构建出稳如磐石的软件系统。**
